## Findings

### B-S1-06-DESIGN-001：`__type_hints__` 合并和覆盖优先级没有闭合

- `kind`：`blocker`
- `requirementOrConstraint`：批准的 ADR-003 第 28–31 行和联合方案 §5.2 要求两层 type hints 按键合并、覆盖层优先；worker snapshot 使用合并视图。`design-plan` 还要求每个必填字段具有 producer、构造责任、consumer 不变量和行为检查。
- `directFact`：`S1-06_设计.md:94-99` 只定义了 `_base_data`、`_base_type_hints` 和运行时 `_type_hints` 的存在，并写明“分别解包”和“保存时过滤到差集路径”，没有规定 base/overlay hints 如何合并、同键冲突由谁覆盖、嵌套提示如何表示和由哪个 consumer 使用。`S1-06_设计.md:118-134` 的测试矩阵只检查“保存后专用 `__type_hints__` 仅保留差集路径”；批准 Items I02 的 required checks（`S1-06_ImplementationItems批准语义.json:29-34`）也没有覆盖 base-only、overlay override、嵌套差集和 merged snapshot 的 hints 语义。
- `currentImpact`：实施者可把 `_type_hints` 只取 overlay、只取 base 或任意顺序覆盖；这样会使 `first_start_time`/`ConfigNode` 类型转换和 `get_serializable_data()` 的 worker snapshot 不符合批准的覆盖优先级，也无法证明 base-only hint 不泄露到专用文件。
- `owner`：原 Issue Worker `/root/s1_06_worker`；若需要改变批准的 type-hint 语义，必须由 Leader 回到方案决策，而不是在实施中选择。
- `correction`：`restore_baseline`。在设计、实施计划和 I02 required checks 中写出唯一规则：两层 hints 按键合并、overlay 同键覆盖 base、运行时 `_type_hints` 服务合并视图；保存时按差集路径过滤，保留差集相关提示、删除 base-only 提示，并明确 dotted path/嵌套表示和 producer/consumer。补充对应的纯函数或公开入口测试映射，不改变 ADR-003 的范围。
- `validation`：读回设计 §5.2–§5.3、受影响保存路径、I02 的六字段和 `test_layered_config.py`/公开入口测试计划；逐项能够定位 base-only hint、overlay override、嵌套差集、`first_start_time` 和 merged snapshot 的输入、预期和证据责任。

### B-S1-06-DESIGN-002：生产缓存键未绑定 `base_config_path`

- `kind`：`blocker`
- `requirementOrConstraint`：联合方案 §5.2 明确要求单例缓存键包含 `base_config_path`；`S1-06_方案决策.md:22-27` 同时要求生产与测试缓存键包含通用层路径，以保证不同两层组合不会复用错误实例。
- `directFact`：`S1-06_设计.md:64-69` 只说明测试缓存键包含专用路径、通用路径、测试标识和 `first_start_time`；I03 的 required checks（`S1-06_ImplementationItems批准语义.json:44-47`）只覆盖无 base 兼容、`ValueError` 和 test_mode 复制，没有生产缓存键的规则或测试。当前源码 `src/config_manager/config_manager.py:120-134` 的 `_generate_production_cache_key` 只接收 `config_path`，`get_config_manager` 在 `:1044-1065` 先按该键命中实例，尚未有 base 维度。
- `currentImpact`：同一专用 `config_path` 先后配合两个不同 base 时，生产 factory 可能返回同一个旧实例，调用方看到的合并视图取决于第一次调用，直接破坏通用层选择和下次启动生效语义。
- `owner`：原 Issue Worker `/root/s1_06_worker`。
- `correction`：`restore_baseline`。明确生产和测试使用规范化的 `(overlay config_path, base_config_path, mode/test identity, first_start_time)` 缓存身份；无 base 时保留现有单文件键兼容。补充“同一 overlay + 不同 base 得到不同实例、同一组合复用同一实例”的 factory 行为检查，并让 lookup 与 create 使用同一 key producer。
- `validation`：读回 public factory 的参数校验、缓存 lookup/create 路径及 I03 required checks；用两个 base 文件和同一 overlay 的固定 fixture 证明实例身份、读取值和无 base 旧行为分别正确。

### B-S1-06-DESIGN-003：基础层失败没有与 overlay `auto_create` 分支形成 fail-closed 传播

- `kind`：`blocker`
- `requirementOrConstraint`：批准方案要求基础层不存在或加载失败时初始化失败、`get_config_manager` 返回 `None`，且不写覆盖层；该语义在 `S1-06_方案决策.md:27`、`S1-06_设计.md:26-28,104-114` 和 ADR-003 第 28–34 行中冻结。
- `directFact`：`S1-06_设计.md:32-47` 将基础层加载失败描述为 `_load` 返回 `False`，再“沿现有存在文件但解析失败路径”返回失败，没有定义可让 `initialize` 区分 base failure、overlay parse failure 和 overlay missing 的结果/状态。当前 `src/config_manager/core/manager.py:163-180` 只根据 `self._config_path` 是否存在和 `_auto_create` 判断是否继续；`src/config_manager/core/file_operations.py:27-69` 对缺失文件和解析失败都返回 `None`。因此若只按设计新增 base load 并返回 `False`，在 base 缺失、overlay 也缺失且 `auto_create=True` 时，现有初始化结构仍可能继续设置 `first_start_time`/paths 并回写 overlay。
- `currentImpact`：基础层这个强制失败条件可能被误当作“覆盖层可自动创建”，产生不应存在的专用文件和运行时记忆，违反基础层只读与 fail-closed 语义；实现者必须自行发明失败原因传递方式。
- `owner`：原 Issue Worker `/root/s1_06_worker`。
- `correction`：`restore_baseline`。在设计中固定 base load 的失败结果/状态和 `initialize` 的短路顺序：base 缺失或解析失败在 `auto_create`、`first_start_time`、路径派生和任一保存入口之前终止；overlay 仍沿既有 `auto_create` 语义处理。补充 base 缺失/损坏且 overlay 存在、overlay 缺失、`auto_create=True/False` 的行为矩阵，均断言返回 `None`、base bytes 不变、overlay 原 bytes 不变或不创建。
- `validation`：读回 `_load`、`initialize`、`FileOperations.load_config` 的错误来源映射和 I02 completion evidence；固定 fixture 覆盖四种组合，并能在公开 `get_config_manager` 入口观察到唯一的 `None`/不写结果。

### B-S1-06-DESIGN-004：保存入口的 required behavior 没有逐项覆盖批准的不变性

- `kind`：`blocker`
- `requirementOrConstraint`：原始需求验收 3 和联合方案 §5.2/§12 要求显式 `save`、autosave、初始化回写都只写覆盖层差集，基础层在保存前后字节/哈希不变；初始化备份也只能来自覆盖层。`reviewer` Skill 要求 `required_behavior_checks` 覆盖真实生产入口行为。
- `directFact`：`S1-06_设计.md:49-62` 文字上声明 `save`、`_delayed_save`、`_save_config_only` 和初始化回写共用差集，但公开测试矩阵 `:122-134` 只有“修改合并结果后保存”的单一保存场景，没有 autosave、初始化回写、初始化备份和各入口的 base/overlay 文件集断言；I02 required checks `S1-06_ImplementationItems批准语义.json:25-34` 也没有把这些入口分别列入行为检查。
- `currentImpact`：实施者可能只在显式 `save()` 接入差集，遗漏 `_delayed_save` 或初始化 finally 分支；当前源代码 `src/config_manager/core/manager.py:199-208,332-377,393-461,513-543` 具有多个独立保存/备份入口，现有设计没有把批准的不变性绑定到每个生产 caller。
- `owner`：原 Issue Worker `/root/s1_06_worker`。
- `correction`：`restore_baseline`。在设计和 I02 required checks 中建立入口矩阵：显式 `save`、progress-only/普通 autosave、`_save_config_only`、初始化回写、初始化备份分别经过同一差集构造；每项都记录 overlay 结果、base bytes/hash、备份路径和失败时旧文件不变。保留现有 watcher/debounce/备份职责，不新增保存机制。
- `validation`：读回受影响路径 §3.2、Review Focus §9、I02 completion evidence 和测试计划；每个真实入口都有可执行的 focused/affected test 定位，随后由 implementation 取得实际测试结果。
