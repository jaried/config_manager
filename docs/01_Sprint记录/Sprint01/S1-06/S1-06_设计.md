## 2. 目标行为与验收闭环

`get_config_manager(config_path, base_config_path=...)` 把 `base_config_path` 作为只读通用层，把 `config_path` 作为可写专用层。读取顺序为“通用层 → 专用层覆盖”，保存只写专用层与通用层的差集。

| 验收 | 生产闭环 | 证据 |
| --- | --- | --- |
| 无 `base_config_path` | 旧的单文件加载、保存、备份、watch 和缓存路径保持原链路 | 既有 `tests/01_unit_tests` 全套通过 |
| 标量覆盖、嵌套合并、列表替换 | `merge_layers(base, overlay)` 递归产生合并快照 | `test_layered_config.py` |
| 专用文件只保存差集 | 所有保存入口统一调用 `diff_from_base(current, base)`；通用文件不写 | 专用文件复读与通用文件 bytes/hash 前后相同 |
| 类型提示只保存差集 | 差集路径过滤 `_type_hints`，不把通用层提示写入专用文件 | 保存后专用 `__type_hints__` 断言 |
| 通用层缺失或解析失败 | base 使用 `auto_create=False`，加载失败直接初始化失败，不覆盖专用层 | `get_config_manager(...) is None`，专用文件 bytes 不变 |
| watch 冲突 | `watch=True` 与 `base_config_path` 同时出现时在入口抛 `ValueError("base_config_path requires watch=False")` | 公开入口异常测试 |
| test_mode | 只复制专用层到隔离目录，base 仍从原路径读取；序列化数据呈现合并结果 | 测试目录文件集合、base bytes 和 `get_serializable_data()` |

## 3. 受影响路径

### 3.1 生产读取路径

```text
get_config_manager(..., base_config_path)
  -> 参数校验与缓存键
  -> ConfigManager.initialize(..., base_config_path)
  -> ConfigManagerCore._load()
  -> FileOperations.load_config(base, auto_create=False)
  -> FileOperations.load_config(overlay, auto_create=批准值)
  -> 解包标准/原始 YAML（保留现有 __data__/__type_hints__ 规则）
  -> merge_layers(base_data, overlay_data)
  -> ConfigNode 重建、_type_hints 保存、路径派生
  -> 公开 ConfigNode 读取
```

通用层加载失败返回 `False`，`initialize` 沿现有“存在文件但解析失败则不覆盖”路径返回失败；`get_config_manager` 返回 `None`。通用层永远不使用 `auto_create=True`。

### 3.2 生产保存路径

```text
公开 set/update 或初始化派生 first_start_time/paths
  -> save / _delayed_save / _save_config_only / 初始化回写
  -> _get_serializable_data() 得到合并后的 plain mapping
  -> diff_from_base(merged, base_data)
  -> 过滤 _type_hints 到差集路径
  -> FileOperations.save_config(_config_path, overlay_envelope, backup_path)
```

`base_config_path` 只参与读取和差集计算。`backup_path` 始终由专用 `config_path` 计算，因此初始化备份只备份专用文件。通用文件不进入任一保存或备份写入口。

`_delayed_save` 的既有分支选择保持不变，只替换最终序列化 payload；progress-only、普通保存和初始化静默保存都经过同一差集构造。

### 3.3 reload 与 test_mode

- `reload()` 重新读取两层并重新合并；base 的新值会反映到内存，overlay 的同名键继续覆盖。
- `test_mode=True` 时，`_setup_test_environment` 只复制或创建专用文件；不复制、不修改 base。实例的 `_true_original_config_path` 继续只指向专用源文件。
- 测试缓存键包含规范化的专用路径、通用路径、测试标识和 `first_start_time`，避免不同 base 共享实例。
- `base_config_path` 与 test_mode 下生成的专用测试路径一起传入 `initialize`；测试序列化读取合并后的完整数据。

## 5. 数据模型与不变量

### 5.1 纯函数

- mapping 以 `collections.abc.Mapping` 判断，返回普通 `dict`，递归复制，输入对象和嵌套对象均不被修改。
- `merge_layers`：base 先复制；overlay 中 mapping 与 base 同为 mapping 时递归；其他类型（包括 list、tuple、标量）由 overlay 整体替换；overlay 新键直接加入。
- `diff_from_base`：merged 中缺失于 base 的键完整保留；两侧都是 mapping 时递归并省略空 mapping；值相等时省略；值不同（含列表变化）完整保留 merged 值。
- 差集只表达 overlay 可写结果，不生成删除标记；批准方案未定义从专用层删除通用键的语义，因此不扩大为 tombstone 协议。

### 5.2 内存状态

`ConfigManagerCore` 增加 `_base_config_path`、`_base_data`、`_base_type_hints` 三个内部字段。`_base_data` 为读取时 plain mapping 快照；公开 `_data` 仍为合并后 ConfigNode 结构。任何 `set/update` 只改变合并内存，不改变 base 快照。

### 5.3 类型提示的 producer、consumer 与优先级

读取时每层解包都产生一份 plain mapping 和一份提示 mapping：

| producer | 构造责任 | consumer 不变量 |
| --- | --- | --- |
| base `FileOperations.load_config` | 读取 base 的 `__type_hints__`；原始格式产生空 mapping | 只作为默认提示，不直接写回 overlay |
| overlay `FileOperations.load_config` | 读取 overlay 的 `__type_hints__`；原始格式产生空 mapping | 同一路径覆盖 base 提示 |
| layered loader | `merged_hints = {**base_hints, **overlay_hints}`，按字符串 key 合并，overlay 同键优先 | `_type_hints` 始终服务合并后的 `_data` / `get_serializable_data()` |
| save payload builder | 用差集路径过滤 `merged_hints` | `__type_hints__` 只含 overlay 差集相关提示，不含 base-only 提示 |

提示 key 沿现有格式保留 dotted path（例如 `paths.work_dir`）；顶层差集键命中该顶层下的全部提示，嵌套差集只命中自身路径或其子路径。提示合并不递归拆分字符串 key，也不把 base-only 值复制到 overlay。`first_start_time` 由现有初始化 producer 写入合并视图，若该键进入差集则保留 `datetime` 提示；`get_serializable_data()` 的 consumer 读取合并 `_data` 与合并 `_type_hints`，保存 consumer 再执行差集过滤。

### 5.4 缓存身份与兼容性

生产和测试 lookup/create 统一使用同一个 key producer：规范化的 `(config_path, base_config_path, mode/test identity, first_start_time)`。生产 key 在显式路径和默认路径都包含规范化 `base_config_path`；无 base 时保留当前单文件 key 形状，保证旧调用兼容。同一专用路径配合不同 base 必须得到不同实例，同一组合必须复用同一实例。`base_config_path is None` 时所有字段、watch、备份和保存 payload 沿当前单文件路径执行。新增参数位于关键字参数之后，不改变既有位置调用。

## 6. 错误语义与恢复

| 情况 | 处理 |
| --- | --- |
| `watch=True` 且提供 base | 入口立即抛固定 `ValueError`，不创建实例、不写文件 |
| base 不存在 | base `load_config(..., auto_create=False)` 返回 `None`；在读取 overlay、`auto_create`、`first_start_time`、路径派生和任一保存入口之前 fail-closed，返回 `None`，overlay 保持原 bytes |
| base YAML 解析失败 | 标记 base load failure，在同一初始化短路点返回 `None`；即使 overlay 缺失且 `auto_create=True` 也不创建 overlay，不写任一层 |
| overlay 解析失败 | 复用当前 overlay 失败语义；存在文件时初始化失败，不覆盖文件 |
| 差集候选校验失败 | 复用 ADR-002 的 `False` 返回和旧专用文件不变；通用文件不触碰 |
| autosave/初始化写入失败 | 返回现有失败值，保留真实错误；不回退为写 base |
| deterministic/runtime 缺口 | 记录 `code/reason/evidence` 和当前 Run/action，保留文档候选，等待 HOST 同一 action 重跑 |

## 7. 测试设计与回归矩阵

### 7.1 纯函数单元测试

`test_layered_config.py` 使用固定最小 dict，覆盖：标量覆盖、嵌套 mapping 合并、列表整体替换、新键差集、相等键省略、空 mapping 省略、输入深层对象不被修改。公开入口测试另外固定 base-only hint、overlay 同键覆盖、嵌套 dotted hint 过滤和 merged snapshot 的 `get_serializable_data()` 结果。

### 7.2 公开入口与文件集成测试

使用 `tmp_path` 建立 `base.yaml` 和 `overlay.yaml`，通过公开 `get_config_manager(..., watch=False)` 验证：

1. 标准格式与原始格式 base 均可读；合并结果完整；
2. base-only hint、overlay override、嵌套 dotted hint 合并和差集过滤符合 §5.3；merged snapshot 的数据与 hints 可由公开序列化接口观察；
3. 显式 `save()` 后 overlay 只含差集，base bytes/hash 前后一致；
4. progress-only/普通 autosave 的 `_delayed_save()` 与 `_save_config_only()` 逐项断言 overlay 差集和 base bytes/hash 不变；
5. 初始化 finally 回写逐项断言 overlay 差集和 base bytes/hash 不变；初始化备份路径只来自 overlay，备份内容不触碰 base；
6. `first_start_time`、派生 `paths` 和专用覆盖项进入 overlay；`__type_hints__` 仅保留差集路径；
7. base 缺失或损坏在 overlay 存在、overlay 缺失、`auto_create=True/False` 四种组合均返回 `None`；overlay 原文件 bytes 不变或不创建，base bytes 不变；
8. `watch=True` 与 base 抛固定 ValueError；
9. 同一 overlay + 不同 base 得到不同生产实例，同一组合复用同一实例；无 base 的既有公开测试保持通过；
10. test_mode 目录只产生专用副本，base 文件不变，`get_serializable_data()` 含合并完整键；
11. `reload()` 读取 base 新值与 overlay 覆盖。

## 9. Review Focus 与完成检查单

- 纯函数是否深拷贝，是否把 list 当 mapping 递归；
- base/overlay `__type_hints__` 是否按 producer → merged consumer → diff filter 顺序闭合，overlay 是否同键优先；
- `get_serializable_data()` 是否消费合并数据与提示，而不是只消费 overlay；
- 生产 cache key 是否包含规范化 `base_config_path`，lookup/create 是否使用同一 producer；
- base load failure 是否在 auto_create、first_start_time、paths 和任何 save 之前短路；
- 显式 save、progress-only/普通 autosave、`_save_config_only`、初始化回写和初始化备份是否逐项证明 base bytes/hash 不变；
- base 是否始终 `auto_create=False`，保存/备份是否绝不使用 base 路径；
- 标准/原始 YAML 的 `__data__`、顶层别名和 `__type_hints__` 规则是否与单文件一致；
- 每个保存入口是否都经过同一差集构造，初始化回写和 autosave 是否漏写完整合并数据；
- 类型提示过滤是否误删嵌套差集或泄露 base-only 提示；
- test_mode 是否只复制专用层，缓存键是否包含 base；
- 无 base 的既有调用与测试是否保持行为不变；
- 失败时是否保持旧专用文件和通用文件字节不变。
