## 目标与冻结失败签名

- 操作链：合法 YAML 包含 sequence → `get_config_manager(...)` → dotted `set(..., autosave=False)` → `save()`。
- 预期：`save()` 返回成功后，已有和更新后的 sequence 均按原值持久化，文件可被安全 YAML parser 重新加载。
- 实际：`save()` 返回 `True`，但保存文件出现 `key:   -`；raw YAML 路径还可出现 `key: &id...   -`。安全解析随后报 `sequence entries are not allowed here`。
- 冻结失败签名：
  1. 保存前输入及初始化后的文件均可安全解析；
  2. `save()` 返回 `True`；
  3. 保存后存在 mapping key 与 sequence dash 被输出到同一行的形态；
  4. 安全 YAML parser 报 `sequence entries are not allowed here`。
- 用户观察定位：`S1-03_原始需求.md#BUG-证据`。

## 结论

### 已核验事实

S1-03 不是 sequence 值本身错误，也不是重复键后处理器制造的错误。根因位于 `ConfigManagerCore` 到 `FileOperations` 的 comment-preserving 保存链路：

1. `ConfigManagerCore._get_serializable_data()` 交出业务值正确的 sequence。
2. `FileOperations._convert_paths_config_nodes()` 的职责名是转换 `PathsConfigNode`，但实现会递归重建所有 `isinstance(value, list)` 的对象。ruamel 的 `CommentedSeq` 也属于 `list`，因此被无条件降级为普通 `list`。
3. `_prepare_data_for_save()` 仅对 `_original_yaml_data` 做顶层浅拷贝，再由 `_deep_update_yaml_data()` 原地修改共享的嵌套 `CommentedMap`。初始化静默保存后，`_original_yaml_data` 中的 sequence 已是普通 `list`，父 mapping key 却仍持有“键与第一条有效序列项之间的注释”元数据。
4. 下一次保存再次把普通 `list` 赋回带有该遗留注释元数据的父键。ruamel dump 首次产出 `stock:   -` 一类非法 YAML。
5. `_remove_duplicate_keys_from_yaml_file()` 对非法 dump 没有任何改动，不是首个偏离点。
6. `save_config()` 在 `os.replace()` 前不重新解析或验证生成的 YAML，因此非法文件仍覆盖目标文件，调用者得到 `True`。

根因可以概括为：**无差别的 list 子类扁平化 + 对原始 ruamel 树的浅拷贝/嵌套原地改写，造成“普通 list 值 + 遗留 sequence 注释元数据”的不一致状态；下一保存周期把该状态序列化成非法 YAML。保存提交前缺少生成结果验证，使损坏被当作成功持久化。**

### 影响边界

- 标准 `__data__` YAML：已复现。
- raw YAML：已复现；非法形态可带 ruamel anchor，如 `stock: &id001   -`。
- `test_mode=True`：已复现。
- `test_mode=False`：在诊断副本上已复现，因此不是测试模式特有缺陷。
- 本次更新的 sequence：已复现，`stock` 的值在序列化前仍正确，但文件被写坏。
- 未显式更新的 sequence：已复现；同一文件中的 `etf` 也被写坏，说明保存全量数据时已有 sequence 同样受影响。
- 没有“键与第一条有效序列项之间注释”的普通 sequence：负对照保存后仍合法；`category_subscription_order` 在当前最小场景中保持合法和值正确。
- 标量和 mapping：当前证据未发现同类失败，机制也特指 sequence 的 dash/注释布局；不把其他容器扩张为本 Issue 的已证实缺陷。
- raw-to-standard 输出中的 anchor/投影重复现象：本次观察到，但未单独诊断为 S1-03 的原子范围；方案必须至少保证 raw 路径不再写出非法 YAML，不能借此扩大到无关的格式重构。

## 首次偏离与数据流

```text
合法 YAML / CommentedSeq + ca.comment
  -> FileOperations.load_config()
  -> ConfigManagerCore 初始化与路径设置
  -> 初始化 _save_config_only()
  -> _get_serializable_data()：业务值仍正确
  -> _convert_paths_config_nodes()：CommentedSeq 被重建为 list
  -> shallow copy + nested in-place merge：父键注释元数据留在共享原始树
  -> 首次 dump：文件仍合法，但内存原始树已进入不一致状态
  -> 后续 set()+save()
  -> 再次 prepare/dump：首次产出 key:   -
  -> duplicate-key 后处理：无变化
  -> 无重新解析校验的 os.replace()
  -> save() 返回 True，目标文件已不可解析
```

首次可观察的文件偏离位于：

`ConfigManagerCore._get_serializable_data()` → `FileOperations._prepare_data_for_save()` → `YAML.dump()`。

更早的状态偏离位于初始化保存周期：`_convert_paths_config_nodes()` 将 `CommentedSeq` 降级，同时 `_deep_update_yaml_data()` 通过浅拷贝共享结构污染 `_original_yaml_data`。

## 竞争原因排除

1. **调用者传入了错误 sequence 值**：排除。`04_manager_pipeline_output.txt` 记录序列化前 `stock=['SSE.600519']`，值正确。

3. **所有 sequence 都会损坏**：排除。无第一项前注释的输入是稳定负对照；当前证据锁定 comment-preserving 布局。

5. **只影响标准 `__data__` 格式**：排除。raw YAML 同样命中解析错误。
6. **只影响 `test_mode=True`**：排除。`test_mode=False` 诊断副本同样复现。
7. **ruamel.yaml 单独随机输出错误**：不成立。最小实验表明失败由“替换带父键注释的 sequence”确定触发；产品代码负责制造并跨保存周期保留该不一致状态。
8. **现有注释测试已经覆盖**：排除。现有通过用例缺少“键与第一条有效项之间的注释”，且未用 parser 重新加载保存产物。
