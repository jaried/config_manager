| 不用任何 YAML 库，手工做文本替换 | rejected | 嵌套路径、sequence、转义、锚点和别名会形成更多分支，无法可靠保证合法 YAML，不是更小等价路径 |
| 使用 Python 标准库输出 JSON 兼容文本作为 `.yaml` | rejected | 虽可被 YAML 1.2 解析，但文件不再保持用户熟悉的 YAML 表达，且日期、路径及扩展类型会增加额外转换规则 |

### 缩小集合

- 选定口径：只保证语义数据一致——文件可解析，键、值、mapping 和 sequence 与保存数据一致；允许注释、空行、引号样式、锚点/别名和原排版被规范化。使用单一安全 YAML 编解码器替代 round-trip 合并逻辑。
- 排除口径：继续保证 round-trip 一致。该口径与用户选择冲突，不进入 solution-v8 候选。
- 合并：无论选择哪一项，保存成功都必须先验证候选可重新加载，再原子替换旧文件；非法候选返回失败且不覆盖旧目标。
- 排除：手写 YAML、正则修改结构、把 JSON 文本伪装成首选 YAML、在口径未确认前修改依赖或产品代码。

### 用户真正的需求

- 用户结果：以最少机制保证 `set()+save()` 后的配置不损坏，sequence 值保持正确，保存成功与实际可重新加载一致。
- 已核验事实：Python 标准库没有 YAML 解析器；当前正式依赖只声明 `ruamel.yaml`，PyYAML 未声明；ruamel 同时用于 `FileOperations` 和 `ConfigManager` 的测试配置、空配置与 raw 内容路径，仓库还存在明确的注释保留测试。因此“整个包移除 ruamel”是依赖迁移，不是单行修复。
- 已解决分歧：用户所说“YAML 一致”只要求 ConfigManager 可观察的数据语义一致，不要求注释、样式、锚点/别名等 round-trip 一致。
- 当前状态：`resolved_by_user`；确认定位为 `S1-03_处理记录.md#2026-08-18-时序-38`。该回复只解决兼容口径，不是 solution-v8 完整方案批准；frame21 继续无效。

### 已确认口径 Q1

1. **只保证数据一致（已选择）**：保存后 YAML 可解析，键值与列表内容一致；允许注释、空行、引号样式、锚点/别名和排版被统一重写。整个包、依赖声明和测试移除 ruamel，由一个 PyYAML YAML 1.2 安全编解码器统一读写。
2. **同时保持注释和格式一致（未选择）**：保存后还保留现有注释、引号样式、锚点/别名和主要排版；需要保留 round-trip YAML 实现。

确认结果：`selected=1`、`status=resolved_by_user`、`reply_locator=S1-03_处理记录.md#2026-08-18-时序-38`。技术验证进一步证明不能直接裸用 `yaml.safe_load/safe_dump`：它会改变 `yes/no/on/off`、前导零整数、`1e3` 和 `1:20` 等标量语义；solution-v8 必须由同一小型 YAML 1.2 resolver 同时约束安全加载和安全输出。
