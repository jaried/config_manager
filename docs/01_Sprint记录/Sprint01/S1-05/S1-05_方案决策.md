## 2. 唯一用户可观察结果

通过公开配置对象执行：

```python
config.progress = new_value
```

自动保存完成后：

1. 主 `config.yaml` 包含新的 `progress` 值；
2. 本次保存没有创建或改写备份；
3. 普通配置、混合配置、未知来源变化和显式 `save()` 继续保留现有通用保存与备份语义。

## 3. 已确认事实与根因

当前产品链路已经满足需求：

```text
ConfigNode.__setattr__("progress")
  -> _schedule_autosave({"progress"})
  -> ConfigManagerCore._delayed_save()
  -> pending_unknown=false 且 pending_roots={"progress"}
  -> _save_config_only()
  -> FileOperations.save_config_only()
  -> 原子写入主 config.yaml
```

现有隔离运行证据为：

- 主文件复读得到 `progress: after`；
- `save_config_only_calls=1`；
- `save_config_calls=0`；
- 备份路径集合与 mtime 保持不变；
- watcher watermark 与主文件 mtime 一致；
- 命令退出码为 `0`。

根因位于正式回归保护：现有测试把“公开属性触发”和“磁盘写入且备份不变”拆成两个用例，没有一个用例贯通完整公开链路。当前问题属于回归保护缺口，不属于生产保存逻辑偏差。

## 5. 方案选择

采用一个独立、确定性的端到端回归测试关闭缺口，生产代码保持不变。

选择依据：

- 直接修复已确认的缺口；
- 不为制造代码变化而改动已经正确的保存路径；
- 不修改 S1-04 已通过测试；
- 一个文件、一个测试函数即可完整证明用户结果；
- 运行时只替换调度时点，不复制产品判断或文件提交逻辑。

## 8. TDD 与验证策略

本 Issue 修复的是“正式回归用例缺失”。产品行为已经处于 green，因此不伪造产品失败。

TDD 证据按以下顺序形成：

1. 在新增文件前运行精确目标路径，记录 `file not found / no tests collected` 的非零退出码，证明正式回归资产缺失；
2. 新增冻结测试，不修改生产代码；
3. 运行新测试，必须从公开属性入口贯通真实保存链并通过；
4. 运行现有 progress focused suite；
5. 运行 affected suite；
6. 运行完整 `tests/`；
7. 运行新增 Python 文件的 Ruff 检查。

测试使用 `tmp_path`、生产类型和生产 YAML codec；无 sleep、网络、数据库、邮件、用户真实配置目录或 teardown 输出。

## 9. 兼容性与不影响既有测试

- 新测试文件使用唯一一级编号 `tc0021`，不会与现有测试重名；
- 每个测试使用独立 `tmp_path`，支持独立和并行运行；
- 不修改已有 fixture、测试函数或 pytest 收集配置；
- 不建立 watcher 线程或真实 timer，避免残留资源与时序波动；
- 不改生产代码，既有功能的行为面保持不变；
- 回归通过标准以“无新增失败”为准，不通过删除断言、改期望或跳过测试取得绿灯。

恢复方式为回退 S1-05 新增测试及阶段提交。配置数据无迁移，也不需要运行时回滚。
