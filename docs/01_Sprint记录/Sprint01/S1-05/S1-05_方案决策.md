## 2. 冻结问题

`config.progress` 变化后，主配置文件必须保存变化后的值，同时该次自动保存不得创建或改写备份。

现有技术证据表明，当前生产链路已经满足上述行为：

```text
config.progress = value
  -> keyed autosave intent: {"progress"}
  -> _delayed_save()
  -> _save_config_only()
  -> FileOperations.save_config_only()
  -> 原子写入 config.yaml
```

当前缺口是正式测试没有用一个独立用例贯通“公开属性变化、自动保存回调、磁盘复读和备份不变”四个观察点。
因此，本 Issue 的修复对象是阶段状态和端到端回归保护，不重新改写已经正确的生产路径。

## 3. 候选方案

### 3.1 方案 A：再次修改生产保存逻辑

- 优点：表面上形成生产代码变更。
- 缺点：当前行为已正确，重复修改会增加回归风险，并违反 KISS、YAGNI 和“不影响已通过测试”原则。
- 结论：不采用。

### 3.2 方案 B：补充独立的完整公开链路回归测试

- 从公开属性入口设置 `config.progress`。
- 使用确定性 autosave seam 捕获并同步执行真实 callback，不依赖 sleep。
- 使用生产 `FileOperations` 和生产 YAML codec 写入、复读。
- 在变化前创建 sentinel backup，并比较路径集合、mtime 和内容。
- 验证只调用 `save_config_only()`，不调用通用 `save_config()`。
- 保持所有生产函数定义、签名、依赖和配置格式不变。

结论：采用方案 B。

## 5. 冻结测试设计边界

新增测试文件和测试函数分别使用唯一编号：

```text
test_tc0021_001_progress_autosave_public_chain.py
test_tc0021_001_001_progress_public_chain_persists_without_backup
```

测试必须满足：

1. 使用 `tmp_path` 隔离主配置和备份，支持独立及并行运行。
2. 使用生产 `ConfigManagerCore`、`FileOperations` 和 `load_yaml`。
3. 只以捕获 callback 的测试 seam 控制执行时点，不复制保存分支逻辑。
4. 先写入 `progress: before`，创建 sentinel backup，再清空观察窗口的调用记录。
5. 通过 `manager.progress = "after"` 启动公开链路。
6. 执行 callback 后，从主配置复读 `progress: after`。
7. 断言通用保存调用为零，仅配置保存调用为一次。
8. 断言备份路径集合、mtime、内容和 `_last_backup_path` 均保持不变。
9. 测试代码遵守文件头、显式 return、120 字符行长和文件不超过 300 行的规范。
10. 测试不连接数据库、不发送邮件、不读取或写入用户生产目录。

## 7. 架构与原则结论

- 职责边界：ConfigManagerCore 继续拥有保存选择，FileOperations 继续拥有文件事务和备份副作用。
- 高内聚：回归测试位于配置管理器单元测试目录，观察一个完整行为。
- 低耦合：测试 seam 只替换调度时点，不替换业务判断、序列化或文件提交。
- DRY：复用生产实现，不在测试中复制 `progress-only` 判断。
- KISS：一个新测试文件、一个测试函数、零生产改动。
- YAGNI：不新增配置项、抽象层、依赖、线程或通用策略。
- 原子性：状态修正、回归保护和待验收投影共同闭合一个 BUG，不拆分新 Issue。
- ADR：`adr_change_set=[]`。
