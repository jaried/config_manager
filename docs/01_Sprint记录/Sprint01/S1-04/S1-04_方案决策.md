## 2. 需求、约束与可观察结果

### 2.1 当前有效需求

1. 通过现有自动保存入口改变根配置 `progress` 时，新值仍保存到主 `config.yaml`。
2. 仅由 `progress` 变化形成的自动保存不执行配置自动备份。
3. 该内部保存完成后，watcher 不再把同一次主文件写入作为新的 mtime 变化处理。

`progress 变化` 指当前能够触发 autosave 的根属性赋值，以及 `set()/update()` 中根段为 `progress` 的键。显式调用 `save()` 仍是调用者主动请求的通用保存，不改成 progress 专用语义。

### 2.2 保留约束

- 普通配置变化继续自动保存并创建现有 best-effort 备份。
- 同一 debounce 批次同时包含 `progress` 与任意普通配置变化时，普通变化占优，整批继续创建备份。
- 外部文件变化仍触发 watcher callback 和 reload；普通内部保存仍保持“不 reload”的现有行为。
- `save() -> bool`、`FileOperations.save_config*() -> bool`、YAML 候选验证、原子替换和备份失败语义不变。
- 不增加配置项、公开参数、持久化状态、外部依赖或消费项目补丁。

### 2.3 一句可观察结果

> 使用方更新 `config.progress` 后能在 `config.yaml` 读到新值，同时看不到该次更新产生或重写自动备份，也看不到 watcher 处理该次内部写入；普通配置保存、显式保存和外部文件监视保持现状。

## 5. 推荐的最小充分方案

只保留一个候选：在现有 `ConfigManagerCore` 保存触发 owner 内携带并合并当前 autosave 批次的变化意图；progress 独占批次在 watcher 的内部写入保护区内复用现有无备份保存，成功后在释放保护区前确认 watermark。

```text
根配置变化
  -> ConfigNode / set / update 只传递根键
  -> ConfigManagerCore 合并 debounce 批次意图
     -> 仅 progress
        -> 进入 watcher 内部写入保护区
        -> 现有 _save_config_only()
        -> 成功后同步当前写入 mtime，再释放保护区
     -> 含普通键或来源未知
        -> 现有 save()，继续自动备份
```

### 5.1 变更边界

| owner / 预计路径 | 最小变化 | 责任 |
|---|---|---|
| `ConfigNode` / `src/config_manager/config_node.py` | 向既有私有 autosave 调度传递已知根键 | 只传播事实，不判断 progress 策略 |
| `ConfigManagerCore` / `src/config_manager/core/manager.py` | 合并待保存根键；普通/未知意图占优；在 `_delayed_save` 选择现有 `save` 或 `_save_config_only`；批次结束清理瞬时意图 | 唯一保存策略 owner |
| `FileWatcher` / `src/config_manager/core/watcher.py` | 让轮询检查与 progress 内部写入共享一个私有 `threading.RLock`；成功时在释放锁前同步自身 watched path watermark 并清除 internal flag；失败时不推进 watermark并清除本次 flag | 唯一 mtime/内部保存同步 owner；兼容 `_save_config_only()` 内再次设置 internal flag |
| focused tests / `tests/01_unit_tests/test_config_manager/test_progress_autosave.py` | 覆盖 progress、普通、混合、watcher 与失败边界 | 独立测试场景与清理 |

`FileOperations`、`AutosaveManager` 和公开 `ConfigManager` API 不修改。

### 5.2 批次规则

- 变化来源明确且全部根键为 `progress`：无备份保存。
- 存在任一非 `progress` 根键：通用保存并备份。
- 调用方没有提供变化键：按现有通用保存并备份。
- progress 独占批次保存失败：在释放 watcher 状态锁前保留旧 watermark、清除本批次意图和 internal flag，并沿用现有 False/日志语义。
- 显式 `save()`：始终保持通用保存语义。

### 5.3 复用与内部排除

- 复用 `_save_config_only()`，避免复制标准包络、YAML 验证和主文件事务。
- 复用现有 AutosaveManager debounce，不改定时器接口。
- 不采用保存前后完整配置快照比较；它会新增 O(n) 状态和比较，变化键已经在入口可得。
- 不让最后一次 mutation 覆盖整批语义；这会在“普通键后跟 progress”时错误跳过备份。
- 不立即同步保存 progress；这会改变现有 debounce 和写入频率。
- 不在 `FileOperations` 按业务键分支；文件层不拥有 progress 语义。

## 6. 适用决策、风险与恢复

### 6.1 架构、接口、状态与 ADR

- 系统边界不变：ConfigManagerCore 仍拥有状态和保存触发；FileWatcher 仍拥有 mtime；FileOperations 仍拥有文件事务。
- 只增加私有参数、私有 watcher 协作入口和 watcher `RLock`；公开 API、配置格式和返回值不变。
- 新状态仅为一个 autosave debounce 批次内的瞬时意图与进程内互斥锁；保存完成或失败后清除意图，均不持久化、不迁移。
- `adr_change_set=[]`。ADR-001 和 ADR-002 只引用，不新增、修订、替代、归档或迁移。
- 没有数据库、网络、前端、跨进程、鉴权、资金、破坏性写入或不可逆迁移变化。

### 6.2 性能

- 普通 autosave 的文件 I/O 和复杂度保持现状。
- progress 独占批次仍执行一次主配置 `O(n)` dump/load/compare/replace，但省去一次备份写入。
- 新增开销为常数级根键意图合并、短持有的 watcher 状态锁和成功后的单次 mtime 读取；不扫描配置树。
- 验收不编造毫秒阈值；以现有 debounce 保存次数不增加、普通路径测试不退化和 progress 无备份写入为完成判据。

### 6.3 决策相关风险

| 风险 | 事件 | 处置/回退 | 残余风险 |
|---|---|---|---|
| `R-01` | 混合批次被误判为 progress-only，普通变化失去备份 | 普通/未知意图占优；专门覆盖两种赋值顺序 | 低 |
| `R-02` | watcher 在主写入与 watermark 确认之间观察中间态，或内部 flag 二次设置造成锁重入问题 | 轮询和 progress 写入确认共用私有 RLock；只有主保存成功才推进 watcher 自身路径的 watermark；验证重入、异常释放及锁释放后的外部 callback | 低；锁只覆盖单次文件事务与状态确认 |
| `R-03` | 某个旧 autosave 调用点没有提供键 | 缺省走通用保存，保持当前备份行为 | 低 |

实施验证失败时不发布实现；恢复方式是保留已批准方案、修正设计或实施缺口后重新运行相应门禁。已发布实现需要撤回时，通过正常 Git revert 恢复旧 autosave 路径；配置文件格式和现有备份不需要迁移。

## 8. 原子性、依赖与点数

- 结论：`keep_single`。

- 外部依赖：无。
- 真实顺序：变化意图传播 → progress 保存选择 → watcher 确认 → focused/regression 验证。
- 估算：保持 Sprint 登记的 `2 points`。
