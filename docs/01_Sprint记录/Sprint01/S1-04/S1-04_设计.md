## 3. 职责与接口差量

### 3.1 ConfigNode 与 facade 只传播事实

- `ConfigNode.__setattr__` 在根管理器上调用 `_schedule_autosave({name})`；它不判断 `progress` 策略。
- `ConfigManagerCore.set()` 以 `key.split('.', 1)[0]` 形成根段；`update()` 一次收集全部根段并只调度一次。
- `ConfigManager.set()` 的公开签名不变。其内部改为先以 `autosave=False` 委托 Core，完成既有 path 投影后再以根段调度一次，从而保留现有“路径更新后调度”顺序并消除当前重复无键调度。
- 无键调用继续表示 unknown intent，必须走通用保存与备份。

只读探针已证实当前 `ConfigManager.set('progress', ...)` 和 `update({'progress': ...})` 都会产生两次无参数 `_schedule_autosave()`。因此 `src/config_manager/config_manager.py` 是 AC-02 的实际适配边界；修改仅限内部参数转发与重复调度消除，不改变批准的公开 ConfigManager API，也不增加业务取舍。

### 3.2 ConfigManagerCore 是批次意图与保存选择的唯一 owner

新增私有瞬时状态：

- `_pending_autosave_roots: set[str]`：当前 debounce 批次已知根段；
- `_pending_autosave_unknown: bool`：存在无键来源；一旦为 true，本批次通用保存；
- `_autosave_intent_lock: threading.Lock`：保护合并、快照和清空。

`_schedule_autosave(changed_roots: set[str] | None = None)` 保留现有递归、保存中、初始化和频率边界：

1. 初始化期间仍只设置 `_need_save`，不污染运行时批次意图；
2. 运行时已加载配置先在 intent lock 内合并事实；`None` 设置 unknown，集合执行 union；
3. 高频保护可以停止重复 timer 调度，但不得丢失已合并的普通根段；
4. AutosaveManager 继续拥有 debounce timer，不修改其接口。

`_delayed_save()` 在 intent lock 内一次性摘取并清空当前批次，再释放 intent lock后执行文件 I/O：

```text
unknown=false 且 roots == {progress}
  -> progress-only
  -> watcher guard（若启用）
  -> 现有 _save_config_only()
  -> 保存成功时确认 watcher watermark

其他集合（普通、mixed、unknown、空集合）
  -> 现有 save()
  -> 现有 backup best-effort 与 bool 语义
```

批次快照与下一批共享状态分离；本批次成功、返回 False 或抛出异常都不把旧意图带入下一批。intent lock 不跨 watcher lock、序列化或文件 I/O，锁顺序不存在反向获取。

### 3.3 FileWatcher 是 mtime 与 internal flag 的唯一 owner

FileWatcher 新增一个私有 `threading.RLock`。下列状态访问统一受它保护：watched path、`_last_mtime`、internal flag/start time，以及一次轮询的分类状态转换。

- progress-only 路径通过 watcher 私有 context guard 持有 RLock；`_save_config_only()` 现有的 `set_internal_save_flag(True)` 在同一线程重入该锁。
- 保存成功时，guard 释放前按 watcher 自己的 `_config_path` 读取 mtime 并更新 `_last_mtime`；随后清除 internal flag。
- 保存失败或异常时不推进 watermark，guard 的 `finally` 仍清除本次 internal flag。
- 普通内部保存继续由现有 internal flag 在轮询时识别并推进 watermark，保持“不 reload”的现状。
- 每次轮询在 RLock 内读取 mtime、判断 internal/external、更新必要状态；外部 callback 在释放 RLock 后调用，避免把 reload 生命周期放入状态锁。

progress 保存完成后 watermark 已等于当前 watched-path mtime，因此下一次轮询不会进入内部变化分支、不会输出内部检测消息，也不会 callback。guard 释放后的真实外部前移仍按普通 external 分支 callback/reload。

## 4. 状态、不变量与失败语义

| 状态/事件 | 不变量 | 失败处理 |
|---|---|---|
| known roots 合并 | union；顺序无关 | 不用“最后一次变化”覆盖批次 |
| unknown 出现 | 本批次普通保存占优 | 不推断未知来源为 progress |
| progress-only 保存成功 | 主文件成功；无 backup；watermark 在 guard 内确认 | 返回既有 bool |
| progress-only 保存失败 | 无 backup；旧 watermark 保留；flag/批次意图清除 | 返回 False/沿用现有日志；后续真实 mtime 变化仍可检测 |
| mixed 两种顺序 | 都进入通用 `save()` | 现有 backup best-effort |
| 显式 `save()` | 永远通用保存 | 不读取 autosave intent 来改变语义 |
| watcher callback | 只对 external 分类调用，且调用时不持有 RLock | 现有轮询异常通道处理 callback 异常 |

无迁移、持久新状态或清理既有 backup。发布后恢复使用正常 Git revert；配置文件格式不变。

## 5. 数据流与并发时序

```text
mutation thread                         autosave timer                  watcher thread
---------------                         --------------                  --------------
known root -> merge intent
             -> debounce reset
                                         detach+clear batch
                                         progress-only?
                                           acquire watcher RLock
                                           _save_config_only()
                                             set flag (RLock re-entry)
                                           confirm watched mtime
                                           clear flag + release
                                                                         acquire RLock
                                                                         current == watermark
                                                                         no detection/callback
external file edit ----------------------------------------------------> classify external
                                                                         update watermark
                                                                         release RLock
                                                                         callback/reload
```

唯一跨线程共享的新业务状态是 autosave intent；唯一 watcher 同步状态由 FileWatcher RLock 保护。两把锁不嵌套。

| 测试组 | 观察点 |
|---|---|
| root mutations | 属性、`set()`、`update()` 的 progress 根段只产生一个 keyed intent；主文件复读新值 |
